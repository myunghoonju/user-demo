## 활용 방식

AI를 설계자가 아닌 검토자이자 토론 상대로 활용  
각 결정은 제가 판단하거나 실무 경험을 근거로 제시  
AI가 대안과 트레이드오프를 제시하면 이를 검토하여 최종 선택하는 방식으로 진행

---

## 단계별 활용 내역

### 1. 요구사항 분석
- 요구사항을 AI에게 입력하고 구현 범위 및 핵심 제약 조건을 정리
- DECISIONS.md에서 다룰 쟁점 후보를 도출

### 2. 아키텍처 설계
- 기술 스택 및 아키텍쳐는 이전에 경험했거나 학습한 내용으로 지정
- 회원가입 시퀀스 (RabbitMQ 비동기, 분산락, DLQ) 상세 설계 검토

### 3. DECISIONS.md 작성
각 쟁점은 단순히 AI 초안을 수용하지 않고 아래와 같이 직접 검토 및 수정

**쟁점 1 — RabbitMQ 비동기 처리:**
- AI 초안의 "서비스 안정성이 더 중요하다"는 표현이 근거가 부족하다고 판단
- Zuul 1 → Spring Cloud Gateway 전환 당시 동기 방식의 장애 전파를 직접 경험한 내용을 근거로 추가

**쟁점 2 — 분산락 및 DLQ:**
- "락 획득 실패 시 그냥 폐기하면 안 되나?"라고 직접 반박
- AI와의 토론을 통해 중복 요청과 경합 실패를 구분할 수 없다는 점, 타임아웃을 길게 설정하면 스레드 풀 마비로 이어진다는 점을 확인하고 DLQ 선택 근거로 반영
- Redis Sentinel 환경에서의 분산락 동작 방식도 직접 질문하여 문서 표현을 수정

**쟁점 3 — 개인정보 처리 전략:**
- soft delete 방식은 실무에서 `deleted_yn` 컬럼 방식으로 직접 사용한 경험을 근거로 단점 구체화
- 탈퇴 이관 작업의 트랜잭션 복잡도 문제를 별도 배치 서비스로 분리하는 방안은 본인이 직접 제안

### 4. 코드 구현
- 헥사고날 아키텍처 패키지 구조 생성 및 도메인 엔티티 구현 시 AI 활용
- 핵심 비즈니스 로직(분산락, DLQ 처리, JWT 인증)은 실무 경험을 바탕으로 직접 판단 후 구현

### 5. 테스트 및 디버깅

**버그 발견 주체**
- 탈퇴 회원 재로그인 가능 버그, 탈퇴 후 동일 이메일 재가입 불가 버그는 AI가 아닌 직접 HTTPie Desktop으로 수동 테스트하다 발견
- AI는 제보된 버그의 원인 분석과 수정 코드 작성을 보조

**Spring Security 디버깅 과정**
- USER 권한 토큰으로 admin 엔드포인트 접근 시 403이 아닌 401이 반환되는 문제에서   
AI가 틀린 수정을 3번 반복 (테스트 기댓값 변경 → `SecurityContextHolder.setContext()` → 명시적 `accessDeniedHandler`)
- 서버 로그를 직접 제공하고 나서야 실제 원인(`sendError(403)` → `/error` 재디스패치 → Spring Security가 익명 사용자로 처리 → 401 반환) 파악
- AI 추론만으로는 한계가 있었고, 실제 로그가 결정적이었음

**설계 수정**
- 탈퇴 플로우(배치 이관 → 즉시 이관)는 계획된 변경이 아니라 수동 테스트 중 발견한 버그로 인해 수정
- 스펙의 의도(탈퇴 데이터 보관 + 파기)는 유지하면서 구현 방식만 조정

**AI가 담당한 보조 작업**
- 통합 테스트 스크립트(`api-test.sh`), Postman 컬렉션, DDL 스크립트 등 반복적 작업
