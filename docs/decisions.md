# 결정사항

설계 과정에서 판단한 주요 쟁점과 선택의 근거를 기록합니다.

---

## 쟁점 1. 회원가입 처리 방식 — 동기 vs 비동기 (RabbitMQ 도입)

### 상황

평소보다 트래픽이 급증하는 상황을 가정  
동기 방식으로 처리할 경우, 요청이 직접 DB에 도달하므로 피크 트래픽에서 DB 커넥션 고갈 및 응답 지연

### 선택

RabbitMQ를 도입하여 가입 요청을 큐에 발행하고, Consumer가 비동기적으로 처리하는 구조를 선택  
API는 큐 발행 성공 시 `202 Accepted`와 `requestId`를 즉시 반환

### 왜 그렇게 판단했는지

| 방식 | 장점 | 단점                    |
|------|------|-----------------------|
| 동기 처리 | 즉시 성공·실패 응답, 구현 단순 | 급격한 요청으로 DB 병목, 응답 지연 |
| 비동기 (RabbitMQ) | DB 직접 부하 차단, 배압 제어 가능 | 즉각적인 가입 결과 응답 불가      |

비동기 방식의 핵심 트레이드오프는 "가입 즉시 성공 여부를 알 수 없다"는 점입니다.  
그러나 동기 방식의 위험성은 실무에서 직접 경험했습니다.  
기존 게이트웨이(Zuul 1)는 동기·스레드 블로킹 방식으로 운영되었는데, 특정 백엔드 서비스의 응답 지연이 게이트웨이 스레드 풀 고갈로 이어지고 결국 게이트웨이 전체가 다운되는 장애 전파를 경험했습니다.   
이후 비동기 방식(Spring Cloud Gateway)으로 전환하여 동일 상황에서도 안정성을 확보했습니다. 회원가입 처리에서도 동기 방식은 트래픽 급증 시 동일한 위험이 있다고 판단하여 비동기를 선택했습니다.  
또한 DLQ(Dead Letter Queue)를 구성하여 락 획득 실패 메시지를 복구합니다.   
DLQ Consumer는 DB에서 이메일·전화번호 존재 여부를 확인한 뒤, 이미 가입된 경우 폐기하고 그렇지 않은 경우 직접 저장합니다.  
동시 중복 저장 경합은 `DataIntegrityViolationException`으로 처리합니다.    
DB 과부하 방지를 위해 DLQ Consumer는 `maxConcurrentConsumers=n`로 제한합니다.

**비용 대비 효과:**
RabbitMQ는 별도 인프라 비용이 발생하지만, 이를 도입함으로써 애플리케이션 서버의 수평 확장 없이도 DB 부하를 Consumer 처리 속도에 맞춰 처리 가능.  
Consumer 수를 조절하는 것만으로 처리량을 탄력적으로 제어할 수 있어, 서버 증설 대비 운영 비용 절감 예상.

## 쟁점 2. 동시 중복 가입 방지 — 분산락 구현 방식 (Redis 도입)

### 상황

비동기 Consumer가 다중 인스턴스로 운영되는 환경에서, 동일한 이메일 또는 휴대전화번호로 동시에 여러 가입 요청이 들어올 경우 데이터 무결성을 보장해야 했습니다.
단순 DB 유니크 제약만으로는 레이스 컨디션 상황에서 예외 처리가 복잡해지고, 불필요한 DB 부하가 발생합니다.

### 선택

Redis 분산락(Spring Integration `RedisLockRegistry`)을 1차 방어선으로 사용하고, DB 유니크 제약을 최종 안전망으로 두는 이중 방어 구조를 선택

- 락 키: `lock:email:{email}`, `lock:phone:{phone}`
- 락 획득 실패 시 중복 요청으로 간주하고 폐기

### 왜 그렇게 판단했는지

| 방식 | 장점 | 단점 |
|------|------|------|
| DB 유니크 제약만 사용 | 추가 인프라 없음 | 다중 인스턴스에서 레이스 발생, 예외 처리 복잡 |
| `setIfAbsent` + Lua 직접 구현 | 세밀한 제어 가능 | 코드 복잡도 증가, 유지보수 부담 |
| `RedisLockRegistry` (선택) | Spring 표준, 코드 단순, 테스트 용이 | Redis Cluster 환경에서 KEYS 커맨드 제약 |

`RedisLockRegistry`는 단일 인스턴스 혹은 센티널 환경에서 안정적이며, 현재 요구사항 범위에서는 적합하다고 판단
향후 Redis Cluster로 전환 시에는 Redisson의 `RLock`으로 교체필요  

**락 획득 실패 시 단순 폐기를 선택하지 않은 이유:**
락 획득 실패 케이스는 두 가지로 나뉩니다. 하나는 동일 이메일·전화번호의 진짜 중복 요청이고, 다른 하나는 트래픽 급증 시 경합으로 인해 정상 요청이 타임아웃으로 실패하는 경우입니다.   
락 획득 실패만으로는 두 케이스를 구분하기 어려움  

타임아웃을 길게 설정하는 방법도 고려했으나, Consumer 스레드가 락 대기로 묶이면 새 메시지 소비가 지연되고 큐 밀림이 가속되는 악순환이 발생합니다.   
`@RabbitListener`는 `maxConcurrentConsumers` 한도의 고정 스레드 풀을 사용하므로 스레드가 무한정 늘지는 않지만, 풀이 모두 락 대기로 고착되면 새 메시지를 소비할 수 없는 사실상 마비 상태가 됩니다. 이 상태가 지속되면 RabbitMQ 큐에 메시지가 계속 쌓여 RabbitMQ 자체 메모리 한도 초과로 이어질 수 있습니다. 따라서 락 타임아웃은 짧게 유지하고, 실패한 메시지는 DLQ로 이동시켜 복구하는 방식을 선택했습니다.

DLQ Consumer는 루프나 재큐잉 없이 DB 상태를 직접 확인하여 저장 또는 폐기를 결정합니다. 이 방식은 큐 순환 루프 위험이 없고, 복구 로직이 단일 클래스에서 명확하게 드러나 가독성이 높습니다.   
또한 DLQ Consumer의 `maxConcurrentConsumers=n` 제한으로 TPS 급증 시에도 DB 복구 부하가 메인 Consumer와 독립적으로 제어됩니다.

**비용 대비 효과:**
Redis는 JWT Refresh Token 저장 및 Access Token 블랙리스트 관리에도 함께 사용되므로, 분산락을 위한 추가 인프라 비용은 발생하지 않습니다.
단일 Redis 인스턴스로 인증 관리와 동시성 제어를 모두 처리할 수 있어 인프라 복잡도 대비 효과가 높습니다.

## 쟁점 3. 회원 탈퇴 후 개인정보 처리 전략

### 상황

회원 탈퇴 시 개인정보보호법에 따라 개인정보를 즉시 파기하거나 분리 보관 후 기간 만료 시 파기해야 합니다.
단순 논리 삭제(soft delete)로 처리하면 법적 요건을 충족하기 어렵고, 즉시 물리 삭제는 분쟁 발생 시 이력 조회가 불가능합니다.

### 선택

탈퇴 회원 정보를 `WithdrawnMember` 분리 테이블로 이관하고, 보존 기간 만료 후 물리 삭제하는 전략을 선택했습니다.

- 탈퇴 즉시 `members` 테이블에서 제거 → `withdrawn_members` 테이블로 이관
- 이름·전화번호는 AES-256 암호화 상태 유지
- 보존 기간 만료 후 스케줄러가 물리 삭제(데모 프로젝트이므로 회원 탈퇴 시 즉시 삭제 및 이관으로 대체)

### 왜 그렇게 판단했는지

| 방식 | 장점 | 단점 |
|------|------|------|
| 즉시 물리 삭제 | 구현 단순 | 법적 분쟁 시 이력 조회 불가 |
| Soft delete (논리 삭제) | 구현 단순 | `deleted_yn = 'N'` 조건 누락 시 탈퇴 회원 데이터 노출 버그 가능, 인덱스 효율 저하, DB 탈취 시 개인정보 노출 범위 증가 |
| 분리 테이블 이관 (선택) | 법적 요건 충족, 운영 테이블 분리 | 이관 로직 및 스케줄러 구현 필요 |

운영 테이블(`members`)을 활성 회원만 유지함으로써 조회 성능을 보호하고, 탈퇴 회원 데이터는 별도 테이블에서 법적 보존 기간 동안만 관리합니다.
또한 탈퇴 즉시 서비스 접근을 차단(Access Token 블랙리스트 등록, Refresh Token 삭제)하여 보안을 보장합니다.

탈퇴 처리와 이관은 하나의 트랜잭션으로 묶어 원자성을 보장합니다.   
탈퇴 시 `withdrawn_members`에 즉시 저장하고 `members`에서 삭제함으로써 이메일·전화번호 유니크 제약이 즉시 해제되어 동일 계정 재가입이 가능합니다. 스케줄러는 이관 역할 없이 보존 기간 만료 데이터 파기만 담당합니다.
